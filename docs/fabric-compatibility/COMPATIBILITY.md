# Fabric compatibility: the database

Compatibility is a claim a player relies on. This page defines the claim format, the test that
backs it, and the rule that a row without a test is not allowed to exist.

Status: **no mod is supported natively yet.** Phase 1 (reading a mod jar) is implemented; Phases 2+
(JVM, Fabric Loader, shim, Fabric API) are not. Rows below are either the project's already
documented verdicts of the **port pipeline** (data/assets carried into a content mod, no Java code)
or marked `untested`. They are not native-runtime claims.

## Phase 1: what reading real jars already proves

Phase 1 does not run code, so it cannot support a mod. It can prove that the engine understands a
real mod set, and that claim is measured, not assumed:

| Fact | Value |
|---|---|
| Jars read | 5 (`sodium-fabric-0.9.2+mc26.3`, `lithium-fabric-0.26.2+mc26.3`, `ferritecore-9.0.0-fabric`, `fabric-api-0.161.0+26.3`, `ImmediatelyFast-Fabric-1.17.1+26.3`) |
| Mods discovered | 58 (jars plus the jars they nest: 5 root jars + Fabric API's 44 modules + Sodium's 9) |
| Load plan | 49 mods load, 9 are inactive duplicates, 0 blocked |
| Diagnostics | 0 errors, 0 warnings |
| Mixin configs | 80, all named in `fabric.mod.json`, none parsed or applied |
| Access wideners | 43 mods declare one |
| Game-class references | 2441 distinct `net/minecraft/*` names across the loaded classes |
| Graphics-class references | 505, the part a native Rust renderer cannot honour |
| Kotlin | 0 of these mods (the Kotlin adapter path is unit-tested, not measured on a real mod) |

Command (the folder is assembled from the SHA-512-verified artifacts pinned in
`tools/benchmark-deps/mods.lock.json`):

```text
horizon-fabric check <mods-folder> --loader-version 0.19.5 --json
```

Two things this run proved about the rules, not just the parser:

- **Duplicate ids are normal.** Sodium embeds its own copies of nine Fabric API modules, which
  collide with the Fabric API download (`fabric-api-base`, `fabric-renderer-api-v1`, …). Loader
  selects one candidate (`ModPrioSorter`); so does this report — the same version, or the newer
  `fabric-renderer-api-v1 17.0.15`, is the copy that loads, and the other is listed as `skipped`
  with the reason. Before this was fixed the run produced 9 wrong "two mods are named" errors.
- **`mixinextras` is a loader dependency, not a mod to install.** Lithium 0.26.2 declares
  `mixinextras >=0.5.5`; Fabric Loader 0.19.5 ships it at `META-INF/jars/mixinextras-fabric-0.5.5.jar`
  (verified by reading the loader jar). The report models it as provided by the pinned loader, so a
  correct mod set no longer looks broken. For any other loader version the check says the bundled
  dependency was not verified instead of guessing.

## Row format

| Field | Meaning |
|---|---|
| `mod` | Modrinth slug and the version tested (`slug@version`, hash) |
| `category` | Performance, optimization, worldgen, biomes, structures, technology, magic, weapons, armor, inventory, minimap, GUI, shaders, resource pack, QoL |
| `tier` | 0 data-only, 1 public API, 2 state mixin, 3 subsystem replacement (ARCHITECTURE.md §4) |
| `native` | `SUPPORTED`, `PARTIALLY_SUPPORTED`, `UNSUPPORTED`, `CRASHES`, `UNTESTED` |
| `compat` | Same values for compatibility mode (real client jar), `UNBUILT` until Phase 6 |
| `basis` | `measured` (harness run, with date), `ported` (port pipeline verdict, with doc link), `design` (architecture says impossible; no test needed), `untested` |
| `evidence` | Harness command or document; an empty field makes the row invalid |
| `date` | When the evidence was produced |

Rules:

- `SUPPORTED` requires a passing end-to-end harness **and** at least one save/load cycle.
- `PARTIALLY_SUPPORTED` requires the harness to fail on a named assertion; "it launched" is not a
  partial support.
- `UNSUPPORTED` requires either a failing harness or a `design` argument naming the layer
  (ARCHITECTURE.md §4) that makes it impossible. "We didn't get to it" is `UNTESTED`.
- `CRASHES` requires the crash file, and the crash must be reproducible twice.
- A row is regenerated by `tools/fabric_compat.py`; hand-edited rows are rejected by its check.
- A mod's verdict is tied to the tested version. A newer version is `UNTESTED` until re-run.

## Categories and the expected ceiling

This is the roadmap's honest expectation, before any test:

| Category | Typical tier | Native ceiling | Why |
|---|---|---|---|
| Resource packs, data packs, structures, biomes, worldgen JSON | 0 | **SUPPORTED** via port pipeline | data, no code |
| Blocks, items, recipes, decoration (Macaw's, Towns and Towers: content) | 0 | **SUPPORTED** via port pipeline | data + registration |
| Tech, magic, weapons, armour, inventory (Create, Botania, AE2) | 2–3 | **UNSUPPORTED** natively until Phase 3+ work | block entities, custom renderers, tick logic |
| QoL, HUD, key binds, commands | 1–2 | **PARTIALLY_SUPPORTED** at best | needs screens, input, events |
| Minimap (Xaero's) | 2–3 | **UNSUPPORTED** natively | draws a world model from client internals |
| Performance/optimization (Sodium, Lithium, FerriteCore, ImmediatelyFast) | 3 | **UNSUPPORTED** by design | they rewrite the renderer/simulation that is Rust |
| Shaders (Iris) | 3 | **UNSUPPORTED** by design | replaces the GL pipeline; Horizon has its own (`docs/shaders.md`) |
| Fabric API itself | 3 (mixins into loader + internals) | **UNSUPPORTED** unmodified | must be forked (option A) or run in compat mode (option B) |

The performance/shaders row is the important one: these are the most-installed mods, and they are
the ones a Rust engine cannot host. The architecture's answer is compatibility mode, not a facade.

## The harness (what `tools/fabric_compat.py` will do)

Not written yet; specified here so the database cannot drift into opinion.

1. Resolve `slug@version` on Modrinth, download the file, check its published hash
   (`tools/runtime.py` already does this for benchmark deps).
2. Phase 1: `horizon-fabric check mods/ --json` must produce a load plan (no JVM). A mod with a
   broken `fabric.mod.json` or an unsatisfied dependency fails here, by design.
3. Phase 2+: start the game with the mod set in a scratch `HORIZON_HOME`, offscreen
   (`horizon-ctl ... launch --offscreen`), and drive a per-mod script:
   - open a fresh world (fixed seed), wait for "ready";
   - the mod-specific action (place its block, open its screen, fire its key bind);
   - save, quit, reopen, assert the state survived;
   - `horizon-ctl quit`, then assert the process exit code and that `logs/` has no unhandled panic.
4. Emit one JSON record per mod: verdict, failed assertion, timings, version, hashes, game build.
5. Multiplayer variants run through `tools/lan_e2e.py` with the mod on both sides.

A mod with no script cannot be `SUPPORTED`. Writing that script is part of supporting the mod.

## Reporting to players

The launcher (`docs/mod-browser.md`) already shows a per-mod verdict before install. For Java mods
it must show two columns once Phase 6 exists: **Native** and **Compatibility mode**, each with its
own value, because they will differ for most mods. A mod that runs in neither is never offered for
install.

## Known impossibility, stated once

A Fabric mod that mixins into `LevelRenderer`, `ClientLevel.tickEntities` or the chunk pipeline
cannot affect Horizon's native runtime: the code it patches does not exist there. That is not a
coverage gap to close; it is the boundary of the design. Rows marked `design` in the table above are
permanent until the engine's architecture changes.
